# اطلس مفهومی شاهنامه — سایت عمومی

سایت عمومی پروژه‌ی «اطلس مفهومی شاهنامه» — معرفی، جست‌وجو و گراف تعاملی، پژوهش‌ها، درباره، و تماس.
همه‌چیز (سایت + دیتابیس) روی **یک** پلتفرم رایگان میزبانی می‌شود: **GitHub Pages** — بدون نیاز
به کارت اعتباری، بدون سرور جداگانه.

## ساختار پروژه

```
index.html          صفحه‌ی معرفی (Home)
atlas.html           اطلس: جست‌وجو (با pagination، دو حالت جست‌وجو) + گراف تعاملی
research.html        پایگاه پژوهش‌ها (مقالات)
about.html           درباره/رزومه — استاتیک
contact.html         فرم تماس (Formspree)

shared.css           سیستم طراحی مشترک (رنگ، فونت، هدر/فوتر تذهیب‌گونه)
shared.js            رسم هدر و فوتر مشترک در همه‌ی صفحات
app-atlas.js          منطق جست‌وجو، pagination و گراف (در atlas.html)

Shahnameh_Atlas.db    خودِ دیتابیس — به‌صورت فایل خام (نه base64، نه embed)
httpvfs-index.js      کتابخانه‌ی sql.js-httpvfs (بارگذاری تکه‌ای/chunk دیتابیس)
sqlite.worker.js      Web Worker موتور SQLite
sql-wasm.wasm         موتور SQLite (WebAssembly)
cytoscape.min.js      کتابخانه‌ی رسم گراف
stats-data.js         آمار خلاصه (سبک، برای صفحه‌ی اصلی/فوتر)

update_data.py        اسکریپت به‌روزرسانی دیتابیس + آمار، بعد از هر ویرایش در DB Browser
favicon.ico, apple-touch-icon.png, logo-full.png, logo-mark-64.png   لوگوی رسمی پروژه
```

## چرا فقط یک هاست؟ (تاریخچه‌ی کوتاه تصمیم)

نسخه‌های قبلی این سایت را روی **Cloudflare Pages** می‌بردیم. وقتی دیتابیس به مقیاس کامل شاهنامه
(~۵۰,۰۰۰ بیت) رسید، بارگذاری اول سایت خیلی کند شد — چون کل فایل دیتابیس یک‌جا در حافظه‌ی مرورگر
بارگذاری می‌شد. راه‌حل، بارگذاری تکه‌ای (`sql.js-httpvfs`) بود که فقط بخش‌های لازم فایل را با
HTTP Range Request می‌خواند.

مشکل بعدی: **Cloudflare Pages از HTTP Range Requests پشتیبانی نمی‌کند** (باگ شناخته‌شده‌ی
خودشان). راه‌حل اول Cloudflare **R2** بود، ولی نیاز به کارت اعتباری داشت که به‌خاطر تحریم در
دسترس نبود. راه‌حل نهایی: **همه‌چیز — هم سایت، هم دیتابیس — روی GitHub Pages** که رایگان است،
کارت نمی‌خواهد، و از Range پشتیبانی می‌کند. این هم مشکل کندی را حل می‌کند، هم دیگر نیازی به
مدیریت دو پلتفرم جدا نیست، هم چون سایت و دیتابیس هم‌مبدأ (same-origin) می‌شوند، حتی نیاز به
تنظیم CORS هم از بین می‌رود.

**تنها استثنا:** فرم تماس، چون GitHub Pages هیچ کد سمت سروری اجرا نمی‌کند، از یک سرویس ثالث
رایگان (Formspree) استفاده می‌کند — جزئیات پایین‌تر.

## راه‌اندازی اولیه (یک‌بار)

### ۱. ساخت ریپازیتوری و آپلود سایت (بدون نیاز به نصب Git)
1. در github.com یک حساب رایگان بسازید (فقط ایمیل لازم است).
2. روی «+» بالای صفحه → «New repository». نامی انتخاب کنید (مثلاً `shahnameh-atlas`)، آن را
   **Public** بگذارید، Create کنید.
3. داخل ریپازیتوری → «Add file → Upload files» → همه‌ی فایل‌های این پوشه (همه‌چیز، از جمله
   `Shahnameh_Atlas.db`) را بکشید و رها کنید → Commit.
4. از Settings → بخش Pages (منوی سمت چپ) → زیر «Build and deployment»، Source را روی
   «Deploy from a branch»، شاخه را `main` و پوشه را `/root` بگذارید → Save.
5. بعد از چند دقیقه سایت روی آدرسی مثل `https://<username>.github.io/shahnameh-atlas/` بالا می‌آید.

### ۲. اتصال دامنه‌ی اختصاصی (atlashanhnameh.ir)
دامنه‌ی شما الان روی Cloudflare است (به‌عنوان DNS). این دو کار را انجام دهید:

**در تنظیمات DNS دامنه (پنل Cloudflare):**
- چهار رکورد **A** برای دامنه‌ی اصلی (`@` یا `atlashanhnameh.ir`) با این مقادیر بسازید:
  ```
  185.199.108.153
  185.199.109.153
  185.199.110.153
  185.199.111.153
  ```
- ⚠️ **بسیار مهم:** برای همین رکوردها، وضعیت Proxy را روی **«DNS only» (ابر خاکستری)** بگذارید،
  نه «Proxied» (ابر نارنجی). اگر Cloudflare به‌صورت پراکسی جلوی GitHub Pages بیاید، همان مشکل
  Range Request که با این مهاجرت حل کردیم دوباره برمی‌گردد — چون درخواست‌ها اول به Cloudflare
  می‌خورند، نه مستقیم به GitHub.

**در تنظیمات ریپازیتوری روی GitHub:**
- Settings → Pages → «Custom domain» → بنویسید `atlashanhnameh.ir` → Save.
  (این خودکار یک فایل `CNAME` در ریشه‌ی ریپازیتوری می‌سازد؛ دست نزنید.)
- چند دقیقه تا چند ساعت صبر کنید تا DNS پخش شود، بعد گزینه‌ی «Enforce HTTPS» را هم فعال کنید
  (گواهی SSL رایگان از Let's Encrypt، خودکار صادر می‌شود).

### ۳. راه‌اندازی فرم تماس (Formspree)
1. در formspree.io ثبت‌نام کنید (پلن رایگان تا ۵۰ پیام در ماه کافی است).
2. یک فرم جدید بسازید، ایمیل مقصد را `abtavakolishandiz@gmail.com` بگذارید.
3. آی‌دی فرم را (چیزی مثل `abcdwxyz`) کپی کنید.
4. در `contact.html`، خط
   ```js
   const FORMSPREE_ENDPOINT = 'https://formspree.io/f/YOUR_FORM_ID';
   ```
   را با آدرس واقعی جایگزین کنید.

اگر Formspree هم به هر دلیلی (از جمله تحریم) در دسترس نبود، فرم به‌طور خودکار پیام خطای مودبانه
با لینک مستقیم ایمیل نشان می‌دهد — سایت هیچ‌وقت خراب نمی‌ماند. به‌عنوان جایگزین کاملاً ساده و
بدون هیچ سرویس ثالث، می‌توانید دکمه‌ی فرم را هم حذف کنید و فقط یک دکمه‌ی `mailto:` بگذارید — به‌
من بگویید اگر این را ترجیح می‌دهید.

## گردش کار: هر بار که دیتابیس را ویرایش کردید

1. در DB Browser for SQLite تغییرات را اعمال و Save کنید (و آن را ببندید — وگرنه مرحله‌ی بعد
   با خطای «File in use» روبه‌رو می‌شود).
2. در همین پوشه:
   ```
   python update_data.py Shahnameh_Atlas.db
   ```
   این کار دیتابیس را برای httpvfs بهینه می‌کند (اندیس می‌سازد، `page_size` را کوچک می‌کند) و
   `stats-data.js` را بازسازی می‌کند.
3. در ریپازیتوری گیت‌هاب، فایل‌های تغییریافته (`Shahnameh_Atlas.db` و `stats-data.js`) را دوباره
   از «Add file → Upload files» آپلود کنید — گیت‌هاب می‌پرسد جای‌گزین شود؟ بله.
4. چند دقیقه صبر کنید تا GitHub Pages نسخه‌ی تازه را دیپلوی کند.

## گردش کار: هر بار که خودِ کد سایت تغییر کرد
همان مرحله‌ی ۳ بالا — فقط فایل(های) تغییریافته را در ریپازیتوری آپلود/جای‌گزین کنید.

## محدودیت‌های GitHub Pages که باید بدانید
- هر فایل تکی تا ۵۰ مگابایت بی‌دردسر است؛ ۵۰–۱۰۰ مگابایت هشدار می‌دهد ولی کار می‌کند؛ بالای
  ۱۰۰ مگابایت نیاز به Git LFS دارد. **حجم `Shahnameh_Atlas.db` را بعد از هر `update_data.py`
  چک کنید** (روی فایل راست‌کلیک → Properties). اگر نزدیک ۵۰ مگابایت شد، خبر بدهید.
- سقف نرم پهنای‌باند: ۱۰۰ گیگابایت در ماه — برای یک سایت پژوهشی معمولی کافی است.
- بدون اجرای کد سمت سرور (به همین دلیل فرم تماس از Formspree استفاده می‌کند).

## استفاده‌ی آفلاین (روی سیستم خودتان، بدون اینترنت)
چون فایل‌ها دیگر با HTTP Range باز می‌شوند (نه base64 embed)، باز کردن مستقیم با دابل‌کلیک
(`file://`) دیگر کار نمی‌کند، و دستور معمول `python -m http.server` هم کافی نیست (تأیید شده:
از Range Requests پشتیبانی نمی‌کند). برای تست محلی:
```
pip install rangehttpserver
python -m RangeHTTPServer 8080
```
سپس در مرورگر به `http://localhost:8080` بروید.

## یادداشت‌های معماری و تصمیم‌های داده‌ای

### نسخه‌ی مسکو (M) تنها نسخه‌ی عمومی است
به‌دلیل ملاحظات کپی‌رایت، `edition='M'` در همه‌جای عمومی سایت سخت‌کد شده — نه فقط فیلتر
پیش‌فرض. کاربر هیچ‌وقت نمی‌تواند به داده‌ی نسخه‌ی خالقی (K) دسترسی پیدا کند.

### گراف: فقط با انتخاب یک گره، فقط همسایگان ۱-۲ جهش
گراف دیگر به‌طور کامل رندر نمی‌شود (چون از چهار منبع تغذیه می‌شود: مدخل↔مدخل، مدخل↔رویداد،
رویداد↔رویداد، و هم‌رخداد با مفاهیم — که رویهم خیلی چگال است). کاربر از یک کادر جست‌وجو یک
مدخل یا مفهوم انتخاب می‌کند؛ فقط همسایگان مستقیم (تا ۲ جهش) نمایش داده می‌شوند. کلیک روی هر
نود، گراف را حول همان نود دوباره می‌سازد.

### دو حالت جست‌وجو
«جست‌وجو در متن بیت» (فقط مصرع‌ها) در برابر «جست‌وجو در همه‌ی محتوا» (معنای امروزی + سایر
خوانش‌ها + نام مدخل/مفهوم مرتبط).

### «سایر خوانش‌ها»
اگر جدول `core_beyt_meanings` رکوردی برای یک بیت داشته باشد، زیر معنای امروزی همان بیت یک
آکاردئون «سایر خوانش‌ها» ظاهر می‌شود — جدا و زیردست پارافریز اصلی. اگر جدول هنوز خالی/موجود
نباشد، این بخش به‌سادگی نمایش داده نمی‌شود (بدون خطا).

### ارجاع علمی صادقانه
کنار «معنای امروزی» هر بیت، فقط ارجاع به تصویر صفحه‌ی اسکن‌شده (`core_page_images`) نشان داده
می‌شود؛ اگر ثبت نشده باشد، پیام «بدون ارجاع علمی ثبت‌شده» می‌آید — هیچ منبعی جعل نمی‌شود.

### صدا — فایل مشترک + timestamp
یک فایل صوتی مشترک برای هر ۱۰ بیت (`core_audio_files`) + بازه‌ی زمانی هر بیت در آن فایل
(`core_beyt_audio_timestamps`). دکمه‌ی «پخش صوتی» فایل مشترک را بارگذاری، به نقطه‌ی شروع seek،
و در پایان بازه‌ی همان بیت خودکار متوقف می‌شود. فایل‌های صوتی باید در پوشه‌ی `audio/` کنار بقیه‌ی
فایل‌های سایت قرار بگیرند و نام‌شان با ستون `file_name` یکی باشد.

### اصطلاحات نمایشی
«پاراف» → «معنای امروزی»، «موجودیت/وجودیت» → «مدخل» — فقط برچسب UI؛ نام جدول/ستون در
دیتابیس (`paraphrase`, `know_entities`) دست‌نخورده مانده.

### ویوهای آماده (v_beyt_summary و…)
اگر این ویوها در دیتابیس موجود باشند، کوئری اصلی جست‌وجو از آن‌ها استفاده می‌کند؛ اگر نبودند،
خودکار به جوین دستی برمی‌گردد — سازگار با هر دو حالت.

### پایگاه پژوهش‌ها
`research.html` مقالات (`res_articles`) را با کلیدواژه، درون‌مایه، منابع، نقد و پیوند به
مدخل‌ها/داستان‌ها نمایش می‌دهد — حتی با یک مقاله هم کامل کار می‌کند.

### پیشرفت پروژه — per-بخش، نه «پایلوت»
واژه‌ی «پایلوت» از کل رابط کاربری حذف شده. نوار پیشرفت در صفحه‌ی اصلی نشان می‌دهد چند درصد
پادشاهی‌ها (`core_sections`) دست‌کم یک بیتِ دارای مفهوم دارند (محدود به نسخه‌ی M).

### فونت
فعلاً `Noto Nastaliq` (پلیس‌هولدر). وقتی فونت خریداری‌شده (`IR Nastaliq`/«ایران بولد») را
فرستادید، فقط کافی است بلوک `@font-face` مربوط به `NotoNastaliq` در `shared.css` را با فایل
جدید جایگزین کنید — بقیه‌ی سایت خودکار عوض می‌شود.

### لوگو و فاوآیکون
لوگوی رسمی (`Atlas_FAV.png` و `Final_Round.png`) جایگزین طرح جای‌گیرنده شد. چون رنگ خط لوگو
(لاجوردی تیره) روی زمینه‌ی تیره‌ی هدر تقریباً ناپیدا می‌شد، در هدر داخل یک چیپ کاغذی‌رنگ (پارچمنت)
قرار گرفت تا کنتراست کافی داشته باشد.

### عنوان انگلیسی
`The Shahnameh Conceptual Atlas` — برای تغییر، مقدار ثابت `ENGLISH_TITLE` در `shared.js`.

### جای ثابت تلگرام/کمک مالی
دو نشان در فوتر همه‌ی صفحات، با برچسب «به‌زودی»، غیرفعال — مستقل از دیتابیس. هروقت لینک واقعی
مشخص شد، در `shared.js` (بخش `footer-social`) جایگزین می‌شود.
